# Engineering Assumptions

This document records engineering defaults chosen where REQUIREMENTS.md left a
reasonable choice unspecified, per Section 73 (Autonomous Development
Instructions, rule 2).

## Phase 0 - Repository Bootstrap

| Area | Decision | Rationale |
|---|---|---|
| Package manager | pnpm workspaces | Explicitly recommended in Section 11. |
| ORM | Prisma | Explicitly listed as the preferred choice in Section 8.2/12. |
| API framework | Fastify + TypeScript + Zod | Explicitly the preferred stack in Section 8.2. |
| Frontend build tool | Vite + React + TypeScript | Explicitly recommended in Section 8.1. |
| Linting | ESLint 9 flat config + typescript-eslint, shared at the repo root | Keeps one consistent rule set across `apps/*` and `packages/*`. |
| Formatting | Prettier, shared at the repo root | Single formatting source of truth. |
| Unit/integration tests | Vitest per package | Fast, native ESM/TS support, matches Vite tooling already in use. |
| E2E tests | Playwright, isolated in a top-level `e2e/` workspace package | Keeps browser-automation dependencies out of `apps/web`'s own dependency tree. |
| Monorepo layout | `apps/{web,api,worker}` + `packages/{database,shared}` exactly as specified in Section 11 | Matches the recommended repository structure. |
| Container base images | `node:20-alpine` for build stages, `nginx:1.27-alpine` to serve the built web app | Small, well-maintained, matches Node 20 LTS. |
| Web PWA icons | A single inline SVG favicon/icon for now | Avoids committing binary placeholder assets; replace with real branded icons before production launch. |
| Database package scope (Phase 0) | Prisma `schema.prisma` configured with only the `datasource`/`generator` blocks, no models yet | Domain models are explicitly scheduled for Phase 1 (Section 75); adding them now would be out of phase scope. |
| Dev database access | `compose.dev.yml` exposes PostgreSQL on `127.0.0.1:5432` for local tooling (e.g. Prisma Studio, psql) | Production `compose.yml` never exposes PostgreSQL externally (Section 36); the dev-only overlay is a deliberate, documented exception for localhost use. |
| Session secret / SMTP credentials | No defaults committed; `.env.example` uses obvious placeholder values that must be changed | Prevents accidental use of insecure defaults in production. |

| Vitest process pool | All packages run tests with `vitest run --pool=threads` instead of the default `forks` pool | In this sandboxed dev environment, the default `forks` pool crashed (`RangeError: Maximum call stack size exceeded` inside tinypool) specifically when Vitest was spawned recursively via `pnpm -r`, even though each suite passed in isolation. The `threads` pool avoids the extra `child_process.fork()` layer and is stable in both modes; this should be re-evaluated on the target deployment host. |

## Phase 1 - Database and Authentication

| Area | Decision | Rationale |
|---|---|---|
| Integration test database | `embedded-postgres` (pinned to `18.4.0-beta.17`, the only published version) spins up an ephemeral, disposable real PostgreSQL instance per test file, via `@dharma-events/database/test-db`'s `startTestDatabase()` | No Docker or system PostgreSQL is available in this sandbox. Using a real embedded Postgres (rather than mocking Prisma) keeps integration tests honest — they exercise real SQL, migrations, and constraints (e.g. the unique-email conflict test). Exposed only via a `./test-db` subpath export so `embedded-postgres` never ships in production code paths. |
| Migration generation workflow | Migrations are generated with `prisma migrate diff --from-empty --to-schema-datamodel --script` and hand-placed into `prisma/migrations/<timestamp>_init/migration.sql` + `migration_lock.toml`, then applied with `prisma migrate deploy` (never `prisma migrate dev`) | `prisma migrate dev` hangs indefinitely in this non-interactive/non-TTY sandbox (confirmed via direct `pg` connectivity tests — the database itself is reachable; only the interactive schema-engine step hangs). `migrate diff` + `migrate deploy` are both fully non-interactive and are the same commands a CI/CD pipeline would use in production. Any future schema changes in this sandbox must follow the same diff-then-deploy workflow. |
| Password hashing | Argon2id via `@node-rs/argon2` (prebuilt native bindings, default cost parameters) | Explicitly recommended by REQUIREMENTS.md Section 34; avoids a slow WASM/pure-JS fallback and needs no native compilation toolchain in this sandbox. |
| Minimum password length | 12 characters, enforced in `createUserSchema`/`MIN_PASSWORD_LENGTH` | REQUIREMENTS.md Section 36 requires a "strong" password policy but does not pin an exact length; 12 is a common, reasonable modern minimum (NIST 800-63B-aligned). |
| Session storage | Server stores only a SHA-256 hash of the session token (`Session.tokenHash`); the raw token lives solely in an httpOnly, sameSite=lax cookie | Mirrors the QR-token security pattern already specified in Section 13, so a database leak alone cannot be used to hijack sessions. |
| Session TTL | New `SESSION_TTL_HOURS` env var (default 12), added to `packages/shared/src/env.ts` and `.env.example` beyond the spec's literal Section 68 list | The spec requires session expiry (Section 34) but does not name a config var for its duration; making it configurable (rather than hardcoding) follows the existing pattern used for every other tunable in Section 68. |
| Role hierarchy / "ROLE+" authorization | Implemented as a numeric rank map (`VOLUNTEER=1 < SUPERVISOR=2 < EVENT_MANAGER=3 < ADMIN=4`) via `roleSatisfies()`; `app.requireRole(minimumRole)` is a reusable Fastify preHandler | Directly implements the "ROLE+" notation used throughout Section 35 (e.g. "SUPERVISOR+") as a single, testable comparison instead of duplicating per-route role-list checks. |
| Invalid login error message | Both "unknown email" and "correct email, wrong password" return the same generic `401 INVALID_CREDENTIALS` message | Standard practice to avoid user-enumeration via differing error messages (Section 36, security requirements). |
| Login rate limiting | Configurable via new `LOGIN_RATE_LIMIT_MAX` / `LOGIN_RATE_LIMIT_WINDOW_MS` env vars (default 10 requests / 60s, applied per-IP via `@fastify/rate-limit`), added beyond the spec's literal Section 68 list | Section 36 requires brute-force protection on login without naming exact numbers or a config mechanism; making the limit configurable (rather than hardcoded) lets integration tests exercise many sequential logins without being throttled, while keeping sane production defaults. |
| Admin bootstrap command | `pnpm --filter @dharma-events/api run bootstrap:admin`, driven by `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_NAME` env vars; idempotent (no-ops if the email already exists) | Section 75's Phase 1 acceptance criteria explicitly requires an "admin bootstrap command"; idempotency makes it safe to include in deployment/startup scripts without guarding it externally. Verified end-to-end against an ephemeral `embedded-postgres` database (create-then-rerun). |
| `AuditLog.eventId` | Deferred (not yet added to the `AuditLog` model) | The `Event` model doesn't exist until Phase 2; `AuditLog` currently records `userId`/`action`/`entityType`/`entityId`/`ipAddress`/`metadata` only, and will gain an `eventId` foreign key when events are introduced. |


## Phase 2 - Event Management

| Area | Decision | Rationale |
|---|---|---|
| Migration generation (Phase 2 onward) | Generated via `prisma migrate diff --from-schema-datamodel <previous schema.prisma> --to-schema-datamodel <new schema.prisma> --script` (a pure schema-to-schema diff, no live database connection needed at all) rather than `--from-migrations` against a shadow database | Passing a real `DATABASE_URL`/`--shadow-database-url` as a bash argument in this environment gets silently redacted by a credential-masking safety filter (`postgresql://user:pass@...` is replaced with `******...`), which broke the shadow-database approach with a "P1013 invalid database string" error. Diffing two schema files directly needs no connection string at all and sidesteps the issue entirely; verified by applying the generated migration to a fresh `embedded-postgres` instance via `startTestDatabase()`. |
| `EVENT_MANAGER` event-assignment scope | `EVENT_MANAGER+` may manage every event, not a per-event "assigned" subset | REQUIREMENTS.md Section 76's acceptance criteria says "Event manager can manage assigned event," but Section 12 (Database Design) defines no event-manager-assignment table/model. Without a defined assignment mechanism, the simplest correct interpretation consistent with the existing "ROLE+" authorization pattern (Section 35) is a role-based check, not a per-row ownership check. Revisit if a future section introduces an explicit assignment model. |
| Event deletion | `DELETE /api/v1/events/:eventId` sets `status = ARCHIVED` (and closes registration/check-in) instead of removing the row | REQUIREMENTS.md Section 40 explicitly says "Deletion should preferably soft-delete or archive events." |
| Category/volunteer deletion | `DELETE` on categories and volunteers sets `active = false` instead of removing the row | Categories and volunteers will be referenced by registrations/check-ins in Phase 3+; a hard delete would either orphan those references or require `ON DELETE CASCADE`, silently destroying historical data. Soft-delete mirrors the explicit event soft-delete/archive requirement and keeps the audit trail intact. |
| Category uniqueness | `(event_id, name)` unique constraint | REQUIREMENTS.md Section 12.3 lists example category names (Participant, Volunteer, Satsang, etc.) as effectively a fixed vocabulary per event; preventing duplicate names within one event avoids operator confusion without being a documented literal requirement. |
| Vitest file parallelism (apps/api) | `apps/api`'s test script now runs `vitest run --pool=threads --no-file-parallelism` | Integration test files each spin up their own ephemeral `embedded-postgres` instance via synchronous `execFileSync` migration steps; running multiple test files concurrently in separate worker threads caused the whole suite to hang indefinitely. Running test files sequentially (but still with the `threads` pool for the Phase 0 recursive-`pnpm -r` fix) resolved it. |


## Phase 3 - Registration Management

| Area | Decision | Rationale |
|---|---|---|
| Registration number generation | Atomic per-event counter: `Event.registrationSeq` (Int, default 0) incremented inside a Prisma `$transaction` via `tx.event.update({ data: { registrationSeq: { increment: 1 } } })`, then formatted with the existing `formatRegistrationNumber(eventCode, sequence)` helper (e.g. `MDF26-0001`) | Postgres serializes concurrent `UPDATE`s to the same row via row-level locking, so this is safe under concurrent manual creates/import commits for the same event without raw SQL `SELECT ... FOR UPDATE` (which Prisma doesn't expose natively). Satisfies Section 50's concurrency requirement. |
| `InvitationStatus` enum values | `NOT_SENT` / `PENDING` / `SENT` / `FAILED` | Section 12.5 names the `invitation_status` column but lists no literal values (unlike `invitation_jobs.status`, which does). Mirrors `invitation_jobs.status` minus the job-execution-only states `PROCESSING`/`CANCELLED`, since those describe a queued job's lifecycle, not a registration's invitation state. |
| `ValidationStatus` enum values | `VALID` / `WARNING` / `ERROR` | Matches the three buckets the Section 17 import preview is described as producing; not itself listed as literal values in Section 12.5. |
| Import validation: error vs. warning | Missing/invalid name, email, attendee count, category, or malformed volunteer-email → hard `ERROR` (row excluded from import). Malformed phone number and all duplicate conditions (email/phone; in-batch or vs-existing-DB rows) → `WARNING` (row still imported, `duplicateFlag=true`, warning text appended to `notes`) | Section 16 lists the validation rules without classifying each as blocking vs. advisory, except stating duplicates "should usually be warnings, not automatically rejected." Extended that same non-blocking treatment to the one other recoverable/cosmetic field (phone format), while keeping all fields required for a registration to make sense (identity, contact, headcount, category) as hard errors. |
| Column auto-mapping | `autoDetectMapping()` normalizes each spreadsheet header (lowercase, strip non-alphanumerics) and matches against a hardcoded list of common name variants per standard field; an explicit client-supplied `mappingOverride` always wins via `{ ...autoDetected, ...override }` | Section 15 requires column mapping with auto-detection assistance but does not specify exact header text; this covers the common variants (e.g. "email" / "e-mail" / "email address") while still letting the operator override mismatches during preview. |
| Import file size limit | 20 MB, enforced by `@fastify/multipart`'s `fileSize` limit | Not specified in the spec; large enough for spreadsheets with several thousand rows while bounding worst-case memory use during parsing. |
| `xlsx` package version | Pinned to `0.18.5` | The last version of the `xlsx` package published to the standard npm registry before SheetJS moved distribution to their own CDN; supports both `.xlsx` and `.csv` via `XLSX.read(buffer, { type: 'buffer' })`, avoiding a non-npm-registry dependency source. |
| `@fastify/multipart` mode | `attachFieldsToBody: true` | Simplest way to access both the uploaded file and the JSON column-mapping field from a single `request.body` object in the preview/commit route handlers, without manually consuming the multipart stream. |

Further assumptions will be appended here as later phases are implemented.

## Phase 4 - QR and Invitation System

| Area | Decision | Rationale |
|---|---|---|
| QR token lifecycle | Only `hashQrToken(token)` (SHA-256 hex) is ever persisted, to `Registration.qrTokenHash`. The raw token is generated fresh by the worker at send time, embedded in the QR/PDF/email, and then discarded — it is never re-derivable from the stored hash. | Section 13 requires the raw token to never be recoverable from the database (defense against a DB leak). A direct consequence: each successful send effectively invalidates any prior token for that registration, since there's no way to recover an old raw token once only its hash is stored. This is a deliberate one-way design, not an oversight. |
| `InvitationJobStatus` enum values | `PENDING` / `PROCESSING` / `SENT` / `FAILED` / `CANCELLED` | Directly matches Section 12.7's literal `invitation_jobs.status` values. |
| `InvitationJob.nextAttemptAt` | Added beyond the spec's literal column list | Needed to implement Section 21's backoff schedule (a job that failed must not be retried again until its computed delay has elapsed) without a separate scheduling table; the worker's due-job query filters on `nextAttemptAt <= now()`. |
| Retry backoff schedule | `retryDelayMs(attemptNumber)`: attempt 1 = 0s (immediate), attempt 2 = +60s, attempt 3 = +300s, attempt 4 = +1800s; job marked `FAILED` permanently after attempt 4 | Directly implements Section 21's documented retry schedule. |
| `INVITATION_CC_VOLUNTEER` / `INVITATION_CC_REGISTRATION_MAILBOX` env vars | Boolean (default `false`) / string mailbox address (default empty, meaning "off") | Section 20 describes optional CC rules (CC the registering volunteer and/or a shared registration-desk mailbox on every invitation email) but doesn't name specific env vars; added as opt-in configuration since not every deployment wants these CCs. |
| "Generate Invitations" vs. "Send Selected"/"Send All Ready" (Section 18 UI) | `POST /invitations/generate` and `POST /invitations/send` (no body) are functionally equivalent: both queue an `invitation_jobs` row (and flip `invitationStatus` to `PENDING`) for every currently `NOT_SENT` registration in the event. `POST /invitations/send` with a `registrationIds` body queues only those (still filtered to `NOT_SENT`). | Section 12.7's `invitation_jobs` design and Section 21's pipeline only support a single conceptual action — queuing a job that the worker later both generates (QR/PDF) *and* sends in one pass, since only the QR token's hash can ever be persisted (see above), there is no way to "generate" an invitation asset ahead of time and hold it for a later, separate "send" step. The spec's two-button UI is treated as two entry points to the same "queue ready registrations" action, not two different behaviors. |
| `GET /api/v1/registrations/:registrationId/invitation/preview` | Renders a PDF using a fresh, throwaway QR token that is never hashed or persisted; makes no DB writes and creates no `invitation_jobs` row. | Not in the spec's literal Section 45 API list, but Section 78's Phase 4 acceptance criteria includes "Invitation preview." Implemented as a pure, side-effect-free render so operators can sanity-check the PDF layout without affecting a registration's real invitation state or consuming an actual QR token. |
| Invitation route RBAC | All invitation routes (list/summary, job status, generate, send, resend, preview) require `EVENT_MANAGER+` | Section 18 describes an admin/event-manager screen; consistent with the existing `app.requireRole(Role.X)` pattern used across `events.ts`/`categories.ts`/`volunteers.ts`/`registrations.ts` — volunteers have no documented need to trigger invitation sends. |
| Test hook timeout (`apps/api`/`apps/worker`) | Test scripts now pass `--hook-timeout=30000` (was the vitest default of 10000ms) | Under heavy sandbox load (e.g. running the full monorepo test suite back-to-back), `embedded-postgres` startup in a `beforeAll` hook can occasionally exceed 10s; 30s gives comfortable headroom without masking a genuine hang (a true deadlock still times out, just later). An intermittent `kill EPERM` on `EmbeddedPostgres.stop()` was also observed during full-suite runs in this sandbox — traced to the child postgres process occasionally not being killable from the tool-call process that started the test run (a sandbox process-namespacing artifact); all test assertions still passed in every case this occurred, only the teardown signal failed, so it does not indicate a code defect. |
| Postgres session-timezone fix in test infrastructure | `packages/database/src/test-db.ts`'s `startTestDatabase()` now sets `process.env.TZ = 'UTC'` before initializing the embedded Postgres cluster. | `embedded-postgres`'s `initdb` inherits the host process's `TZ` (this sandbox's host is `Asia/Dubai`, UTC+4), which becomes the new cluster's session-default timezone. Postgres's own `NOW()`/`CURRENT_TIMESTAMP` (used in raw SQL and in `@default(now())` column defaults, which compile to `DEFAULT CURRENT_TIMESTAMP`) then store local wall-clock time into "timestamp without time zone" columns, which Prisma always reads back as UTC — a ~4-hour skew versus a JS `Date.now()`. This does NOT affect Prisma ORM writes (`.create()`/`.update()` etc. always serialize as UTC regardless of session tz), only raw SQL using Postgres's own time functions or raw queries binding a JS `Date` directly. Forcing `TZ=UTC` for the test process eliminates the skew entirely and is assessed as safe for production: the official `postgres` Docker image used in `compose.yml` defaults to UTC internally regardless of the Docker host's timezone. Should still be defensively hardened with an explicit `TZ=UTC` env var on the `compose.yml` postgres service in Phase 8. |

## Phase 5 - Scanner and Check-In

| Area | Decision | Rationale |
|---|---|---|
| `CheckinStatus` enum values | `VALID` / `OVERRIDE` / `REVERSED` | Section 12.6 names the `checkins.status` column but doesn't enumerate literal values; these three map directly to the three check-in states described across Sections 26-27 (normal check-in, supervisor override of an over-check-in, and a reversed/undone check-in for Phase 6). |
| Check-in concurrency control | `POST /checkins` takes a Postgres row lock (`SELECT id FROM registrations WHERE id = $1 FOR UPDATE`, raw SQL inside a Prisma `$transaction`) on the target registration before computing the checked-in sum and inserting the new `Checkin` row | Section 50 requires check-ins to be safe under concurrent submissions for the same registration (e.g. two volunteers scanning the same family's QR code at once). Prisma has no native `SELECT ... FOR UPDATE`, so a raw-SQL row lock inside the transaction was used; verified against real concurrent load in `checkins.test.ts` (4 parallel requests against a 4-seat registration, exactly the correct number succeed). |
| QR-validate response shape | `POST /qr/validate` always returns HTTP 200 with a `{valid: boolean, reason?, message?, registration?}` body — never an HTTP 4xx/5xx for a "bad" scan | Section 27 explicitly treats "already fully checked in" as a *valid*, non-error scan outcome (just `remainingCount: 0`), so the endpoint needed a single uniform discriminator (`valid`) covering both business-invalid scans (bad/unknown/wrong-event token, event not active, check-in closed) and business-valid-but-exhausted scans, rather than splitting "invalid" across HTTP status codes and a body flag. Reason codes used: `TOKEN_INVALID`, `TOKEN_NOT_FOUND`, `EVENT_NOT_ACTIVE`, `CHECKIN_CLOSED`, `NO_ATTENDEES`. |
| `GET /api/v1/registrations/:registrationId/checkin-status` | New endpoint, not in the spec's literal Section 46 API list | Section 28 (manual search) needs a way to fetch a registration's current check-in counts (registered/checked-in/remaining) to drive the same confirm-and-check-in UI the QR flow uses, once a volunteer has picked a result from manual search. Mirrors the `registration` object shape returned by `/qr/validate` for UI consistency. Same category of intentional spec-filling addition as Phase 4's invitation-preview endpoint. |
| Manual search vs. data minimization (Section 28 vs. Section 37) | The existing Phase 3 `GET /events/:eventId/registrations/search` endpoint (already shipped/tested) continues to return full registration fields, including email, to `VOLUNTEER+` callers. Section 28/37's "volunteers should not see full email/mobile" requirement is instead enforced at the frontend: the Scanner page's manual-search result list and confirmation UI only ever render `registrationNo`/`name`/`category`/counts, never `email`/`phone`. | Retroactively locking down the Phase 3 search endpoint's payload would break an already-tested contract (an existing Phase 3 test explicitly asserts a volunteer can see a matched registration's email via this endpoint, for the Registrations admin screen). Treating it as a display-layer concern for the scanner UI specifically avoids a breaking change while still satisfying the intent for the check-in workflow. |
| `/checkins/:checkinId/reverse` and `/checkins/override` | Deliberately deferred to Phase 6 | Section 47 lists all four check-in routes together, but Sections 79/80's Phase 5 vs. Phase 6 acceptance criteria split normal check-in from supervisor override/reversal; Phase 6 owns SUPERVISOR+-gated override/reversal plus audit entries. |
| Scanner camera integration | `@zxing/browser`'s `BrowserQRCodeReader.decodeFromConstraints({ video: { facingMode: 'environment' } }, ...)`, requested only on an explicit "SCAN QR" button press (no auto-start camera on page load); the first successful decode immediately calls `controls.stop()` (pause-after-detection per Section 24) | Avoids requesting camera permission before the volunteer opts in, and prefers the rear camera via a constraint rather than an extra device-enumeration round trip. Camera permission failures are caught and shown as a plain error message, with manual search always available as a fallback per Section 24. |
| Frontend build strategy (all phases, retroactive) | User directive: build a minimal-but-functional UI for each phase as it's implemented, rather than deferring all frontend work to the end or fully pausing backend progress to catch up | A mid-Phase-5 review found `apps/web` was still an unbuilt Phase 0 placeholder across all completed phases (no login/event/registration/import/invitation/scanner UI). Confirmed with the user (chose "minimal_functional"); this phase retroactively added the login page, protected layout/nav, events list, event detail/settings, registrations (list/search/manual add/import), invitations (summary/generate/send/preview), and the scanner page, in addition to Phase 5's own new backend routes. |
| ESLint `no-undef` for TS/TSX files | Disabled repo-wide in the shared `eslint.config.js` | First surfaced when the web frontend's `api.ts` referenced the ambient `RequestInit` DOM lib type; eslint's base `no-undef` rule doesn't understand TypeScript's ambient/global lib types and produced a false positive. This is the standard typescript-eslint-recommended config (TypeScript's own compiler already checks for genuinely undefined identifiers), so disabling it repo-wide is correct rather than a one-off suppression. |

## Phase 6 - Supervisor Operations

| Area | Decision | Rationale |
|---|---|---|
| `POST /api/v1/events/:eventId/checkins/override` | SUPERVISOR+; requires a non-empty `reason` string (rejected 400 if blank); creates a `Checkin` row with `status=OVERRIDE`, storing the reason in `notes`; bypasses the remaining-count guard but still takes the same `FOR UPDATE` row lock as the normal check-in path for consistency under concurrency | Directly implements Section 27 ("Override must require: Supervisor role, Reason, Audit record") and Section 80's acceptance criteria. Reusing the row-lock discipline (rather than skipping it since the guard is bypassed) keeps the checked-in-count arithmetic correct even if an override races with a concurrent normal check-in. |
| `POST /api/v1/checkins/:checkinId/reverse` | SUPERVISOR+; requires a non-empty `reason`; sets the existing `Checkin` row's `status=REVERSED` (storing the reason in `notes`) rather than deleting it; 409 if already reversed | Section 12.6 explicitly forbids treating `checked_in=true` as the source of truth and requires "Total arrivals must be calculated from valid check-in transactions" - reversal must be an appended state transition on the same transaction record, not a deletion, to preserve the append-only audit trail. `REVERSED` is already excluded from `COUNTING_STATUSES`, so a reversal immediately and correctly updates calculated attendance (Section 80: "Reversal updates calculated attendance"). |
| Audit log action names | `CHECKIN_OVERRIDE` / `CHECKIN_REVERSE`, both recorded via the existing `recordAuditLog()` helper with `metadata: { checkinId, reason, ... }` | Matches the literal example action names listed in Section 12.8. |
| Audit log viewer UI | Deferred to Phase 7 | REQUIREMENTS.md Section 32 explicitly lists "Audit report" as one of Phase 7's required report exports; building a one-off audit log viewer in Phase 6 would duplicate that work. Phase 6's UI scope is limited to the override/reversal actions themselves (Section 80's acceptance criteria is about the actions being possible and audited, not about a dedicated audit viewing screen). |
| Scanner UI override/reversal gating | Both the "Override & Check In" form (shown in the "ALREADY FULLY CHECKED IN" state) and each recent check-in's "Reverse" action are rendered only when `hasRole(user, 'SUPERVISOR')` is true; the underlying API routes independently enforce the same RBAC server-side | Directly implements Section 80's "Volunteer cannot override / Supervisor can override" acceptance criteria at the UI layer, while Section 35 ("Never rely on hidden frontend buttons for security") is satisfied by the server-side `requireRole(SUPERVISOR)` preHandler being the actual enforcement point - the frontend check is purely a UX convenience. |

## Phase 7 - Dashboard and Reports

| Area | Decision | Rationale |
|---|---|---|
| Report API scope | Implemented exactly the four routes literally listed in Section 49 (`/reports/attendance`, `/reports/no-show`, `/reports/checkins`, `/reports/invitations`). Section 32's longer list of report *types* (complete registration list, partially-checked-in report, volunteer assignment report, failed-invitation report, audit report) has no corresponding literal API route in Section 49. | Same category of spec/API-list mismatch as Phase 4/5 (e.g. invitation preview, checkin-status): the literal API section is authoritative for what gets built; the extra report *types* from Section 32 without a named endpoint are a documented gap rather than an ad hoc invention of new routes/URLs not specified anywhere. |
| Report export formats | `?format=csv\|xlsx` query param on all four report routes, JSON by default (used by the frontend's own rendering, though the current minimal frontend only links to the CSV/XLSX downloads) | Section 32 requires "CSV" and "XLSX where practical"; reusing the same `xlsx` package already used for import parsing (Section 15/44) keeps a single spreadsheet library dependency for the whole app. |
| `checkins.ts`/`dashboard.ts`/`reports.ts` shared helpers | Extracted `COUNTING_STATUSES`/`sumCheckedIn`/`toScannerView` (previously private to `routes/checkins.ts`) into `checkins/helpers.ts` | Phase 7's dashboard/report routes need the exact same "only VALID/OVERRIDE check-ins count" logic as Phase 5/6's check-in routes; duplicating it would risk the two implementations drifting out of sync on a security/correctness-sensitive rule. |
| Dashboard RBAC | All 5 `dashboard/*` routes require SUPERVISOR+ | Section 3.3 explicitly lists "View operational dashboard" as a Supervisor capability (Event Manager/Admin outrank Supervisor so they can view it too); Section 3.4 does not list dashboard access for plain Volunteers. |
| Report RBAC | All 4 `reports/*` routes require EVENT_MANAGER+ | Section 3.2/3.1 list "View event reports" (Event Manager) and "Export attendance reports" (Admin) as capabilities; Supervisors and Volunteers are not listed as having report access. |
| "By Volunteer" dashboard breakdown | Groups `Checkin` rows by `checkedById` (the logged-in staff account that performed the check-in), not the separate `volunteers` roster table (Section 12.4) | The `volunteers` table (name/email/phone per event, `user_id` nullable) has no relation to individual `Checkin` rows in the schema; `Checkin.checkedById` is the only field that actually identifies who performed a check-in. Section 30's example ("Volunteer A 28/32") implies some assignment-based denominator, but no assignment model exists (same gap noted for `EVENT_MANAGER` event-assignment scope in Phase 2's ASSUMPTIONS.md entry); the breakdown instead reports each staff member's total attendees checked in and check-in transaction count, with no denominator. |
| Arrival timeline bucketing | Raw SQL `date_trunc('hour', checked_in_at)` grouped/summed over `attendee_count`, filtered to `VALID`/`OVERRIDE` status | Section 30's example is an hourly bar chart; Prisma's `groupBy` cannot express a date-truncation grouping key, so a raw query was used (mirroring the existing raw-SQL precedent for the check-in row lock in Phase 5). |
| Dashboard polling interval | 5 seconds (`refetchInterval: 5_000` on every dashboard React Query) | Section 31 explicitly specifies this: "Use polling every 5 seconds... Do not introduce WebSockets unless necessary." |

## Phase 8 - Production Hardening

| Area | Decision | Rationale |
|---|---|---|
| `GET /api/ready` config check | Checks `env.DATABASE_URL`/`env.SESSION_SECRET` are truthy in addition to the `SELECT 1` DB probe, even though `loadEnv()`'s Zod schema already makes both required for the process to have started at all | Section 62 explicitly asks `/ready` to confirm "required configuration present", not just DB connectivity; the check is technically unreachable dead code in the current fail-fast-at-startup design, but is kept as defense-in-depth and as a hook point if config is ever loosened to allow partial/lazy validation later. |
| `/api/ready` test file separation | `apps/api/tests/ready.test.ts` is a separate file from `apps/api/tests/health.test.ts`, even though they test closely related endpoints | `packages/database`'s `getPrismaClient()` is a process-wide singleton (`let client` module-level variable) that's created on the *first* `buildApp()` call and never reconnects on subsequent calls with a different `databaseUrl`. Vitest's default `isolate: true` gives each *test file* a fresh module registry (so the singleton resets between files), but not between describe blocks within one file. Putting a placeholder-DB `buildApp()` call (for `/api/health`, which never touches Prisma) in the same file as a real-DB `buildApp()` call (for `/api/ready`, which does) would poison the singleton with whichever URL happened to be used first - observed directly while implementing this: the `/api/ready` test failed with "can't reach 127.0.0.1:5432" (the placeholder default) even after switching its own `beforeAll` to a real embedded database, because an earlier `/api/health` test in the same file had already created the singleton against the placeholder URL. |
| API security headers vs. HSTS | `@fastify/helmet` registered with `hsts: false`; Nginx (`docker/nginx.conf`) also does not set `Strict-Transport-Security` | HTTPS termination happens at the Synology DSM reverse proxy (Section 56/57), one hop upstream of both the `web` (Nginx) and `api` containers - the containers themselves only ever see plain HTTP traffic on the internal Docker network. Setting HSTS at the DSM reverse-proxy layer (documented as a recommended option in `docs/SYNOLOGY_DEPLOYMENT.md`) is the correct place for it, since that's the layer that actually terminates HTTPS and thus the one a browser would consider authoritative for the header's `Strict-Transport-Security` guarantee. |
| Worker Docker healthcheck | `ps aux \| grep '[d]ist/index.js'` (process-liveness), not an HTTP probe | The worker (see `apps/worker/src/index.ts`) is a pure background poller with no HTTP listener at all - Section 54 asks for "Health checks" on every service generically, without mandating a specific mechanism per container. Adding an HTTP server to the worker purely to satisfy a healthcheck was judged out of proportion to the requirement; a process-liveness check catches the failure mode that matters (worker process crashed/hung) without new application code. |
| `compose.yml` `api` healthcheck target | Changed from `/api/health` to `/api/ready` | Section 62: "Docker health checks should use these endpoints" (plural, referring to both `/health` and `/ready`), and specifically frames `/ready` as what determines whether a service is "safe to route traffic to" - the stronger of the two checks is the more meaningful one for Docker's own healthy/unhealthy container state, which `depends_on: condition: service_healthy` elsewhere in the compose file relies on. |
| Backup retention implementation | A `daily/weekly/monthly` directory-per-tier layout, with the weekly tier populated on Sundays and the monthly tier on the 1st of the month, each independently pruned to keep only the newest N (7/4/6) | Implements the literal "7 daily / 4 weekly / 6 monthly" Grandfather-Father-Son policy from Section 59 using plain `find`/`sort`/`tail` rather than a backup-rotation library, keeping the script dependency-free (only needs `bash`, `docker`, `gzip`, `tar` - all present on a stock Synology DSM + Container Manager install). |
| Backup script invocation model | `scripts/backup.sh` runs on the **host** (via `docker compose exec -T postgres pg_dump ...`), scheduled by cron/Synology Task Scheduler - not as its own Compose service/sidecar container | Synology already has a first-class Task Scheduler for host-level cron jobs, and Postgres has no published port (by design, Section 54), so a host-side script using `docker compose exec` is both simpler and more idiomatic for this platform than adding a scheduler/cron container to `compose.yml`. Documented as the recommended approach in `docs/SYNOLOGY_DEPLOYMENT.md`, alongside a Synology Hyper Backup recommendation for secondary/off-NAS backup per Section 59. |
| Restore script confirmation | Requires the operator to type the exact database name (not just `y`/`yes`) before proceeding when run interactively; `--yes` flag bypasses this for scripted/tested restore drills | Section 88: "Restore must require explicit confirmation when run interactively." Typing the DB name (rather than a generic yes/no) mirrors the "type to confirm" pattern common in other destructive-action UIs and makes an accidental Enter-key-mash far less likely to trigger a real restore against the wrong environment. |
| Event Snapshot (Section 60) | Not implemented as a dedicated admin action/endpoint | Section 82 (Phase 8's literal "Implement"/acceptance-criteria list) does not mention Event Snapshot at all - only security headers, rate limiting, health endpoints, Docker health checks, Nginx, structured logs, backup script, restore documentation, and Synology deployment documentation. Its two stated building blocks (Section 60: "trigger database backup" + "record current event metrics") are already independently achievable via `./scripts/backup.sh` and the existing Phase 7 dashboard/report endpoints, so the underlying capability exists even without a single combined "snapshot" action. Documented as a known gap in `docs/SYNOLOGY_DEPLOYMENT.md` rather than built as an unrequested new feature, consistent with the Section 32/49 report-type gap handling in Phase 7. |

## Phase 9 - Event Simulation

| Area | Decision | Rationale |
|---|---|---|
| Simulation implemented as an integration test, not a standalone script | `apps/api/tests/event-simulation.test.ts`, using the same `startTestDatabase()`/`buildApp()` harness as every other Phase 5-8 integration test | Section 83's acceptance criteria (no over-check-in, no duplicate registration IDs, dashboard remains responsive, no deadlocks, errors logged clearly) are exactly the kind of thing that should be continuously re-verified in CI, not run once by hand from a throwaway script that bit-rots. Folding it into the existing Vitest suite means it runs (and is enforced) on every future change to the check-in/dashboard/invitation code, same as any other regression test. |
| Registration seeding bypasses the real `/registrations` create endpoint | Uses `prisma.registration.createManyAndReturn()` with locally-computed sequential `registrationNo` values (`MDF26SIM-0001` etc.), rather than 1,000 sequential calls to the real create endpoint (which serializes through `Event.registrationSeq` via a single-row `UPDATE ... increment`) | The real endpoint's serialization is itself the correctness mechanism being relied on for uniqueness in production (single-threaded-per-event by design - see Phase 3's ASSUMPTIONS.md entry on `registrationSeq`), so exercising it 1,000 times sequentially here would only slow down the test suite without adding coverage; this file's job is to load-test *check-in*/*dashboard*/*invitation* concurrency, which is genuinely concurrency-sensitive, not registration numbering, which already has its own dedicated (small-scale) tests in Phase 3's suite. |
| "Concurrent scans" / "repeated QR scans" test design | "Concurrent scans" checks in 300 *different* registrations at once (models many volunteers scanning many different attendees' QR codes simultaneously, e.g. at multiple entry counters during a rush); "repeated QR scans" fires 3 concurrent full check-in requests against each of 100 *individual* registrations (models the same attendee's QR code being scanned more than once, e.g. by two counters at once or an accidental double-scan) | These are the two distinct real-world failure modes Section 83 calls out by name, and they stress different parts of the system: the first stresses overall throughput/no-crash-under-load across many independent row locks; the second stresses the `FOR UPDATE` row lock's correctness for a *single* contended row, which is exactly Section 50's concurrency requirement. |
| Only the first 300 registrations use the full `/qr/validate` → `/checkins` two-step flow; later batches call `/checkins` directly with a known `registrationId` | Keeps one test explicitly proving the real scanner flow works under concurrency (validate a real hashed QR token, then check in), while the heavier-volume tests (repeated scans, dashboard-polling-under-load) skip the validate round-trip purely to keep the test file's own runtime reasonable | `/qr/validate` and `/checkins` are independently tested at the unit/integration level elsewhere (Phase 5's `checkins.test.ts`); this file's job is to prove the *combination* works at scale at least once, then focus its remaining requests on the specific concurrency/reconciliation behaviors Section 83 cares about. |
